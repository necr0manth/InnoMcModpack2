# InnoMcModpack2

Репозиторий содержит файлы модпака и скрипт для подготовки отдельных клиентской и серверной сборок.

## Локальная сборка

Требуется Python 3. Запускайте команды строго из корня репозитория: скрипт использует текущий рабочий каталог как источник файлов.

```powershell
# Собрать клиент и сервер
python build_pack.py

# Собрать только клиент
python build_pack.py client

# Собрать только сервер
python build_pack.py server

# Задать каталог результата для одного режима
python build_pack.py client -o C:\Temp\InnoMcModpack2-client
```

По умолчанию результаты создаются в `build/client` и `build/server`. Локальная сборка создаёт каталоги с готовыми файлами, а не ZIP-архивы.

> **Внимание:** перед сборкой целевой каталог полностью удаляется и создаётся заново. Не указывайте через `-o` каталог с ценными файлами. Параметр `-o` применяется только при сборке одного режима (`client` или `server`) и игнорируется при сборке обоих режимов.

Если запуск выполняется внутри Git-репозитория, скрипт предварительно вызывает `git lfs pull`. При недоступном Git LFS сборка продолжится с уже имеющимися локальными файлами, поэтому перед публикацией проверьте, что LFS-объекты загружены.

## Состав сборок

- Клиент: корень репозитория, отфильтрованный правилами `.packignore`.
- Сервер: корень репозитория, отфильтрованный сначала `.packignore`, затем `.client_files`.
- При базовом копировании всегда исключаются `.git`, `.github`, `.idea`, `build`, `__pycache__`, `.client_files`, `.packignore`, `server_pack` и `build_pack.py`, независимо от правил фильтрации.
- После основной серверной копии содержимое `server_pack/` рекурсивно накладывается поверх результата. Файлы с теми же путями перезаписываются; правила `.packignore` и `.client_files` к этому overlay не применяются.
- Сам каталог `server_pack/` не попадает в базовую клиентскую или серверную копию: его содержимое добавляется только финальным серверным overlay.
- `.gitignore` влияет только на Git и не управляет составом сборок.

Практическое размещение файлов:

| Назначение | Что сделать |
| --- | --- |
| Клиент и сервер | Хранить файл в корне репозитория и не исключать его правилами. |
| Только клиент | Хранить файл в корне и добавить его путь в `.client_files`. |
| Только сервер | Хранить файл по нужному относительному пути внутри `server_pack/`. |
| Ни одна сборка | Добавить путь в `.packignore`. |

В `.packignore` и `.client_files` указывайте по одному шаблону на строку. Пустые строки и строки, начинающиеся с `#`, игнорируются. Правила применяются по порядку, поэтому более позднее совпадение имеет приоритет; правило с `!` может повторно включить ранее исключённый путь, только если обход не был остановлен на исключённом родительском каталоге.

## CI и релизы

GitHub Actions собирает оба режима и публикует артефакты `client-pack` и `server-pack`. Для тегов вида `v*` содержимое сборок дополнительно упаковывается в ZIP-файлы и прикладывается к GitHub Release.

## AutoModpack и деплой

Оба workflow деплоя собирают клиентскую и серверную сборки. Серверная сборка публикуется в `TARGET_DIR`, а клиентская — в `TARGET_DIR/automodpack/host-modpack/main`, откуда AutoModpack раздаёт её игрокам. Клиентская поставка включает отфильтрованные файлы сборки, в том числе конфиги и KubeJS; серверный overlay остаётся только в серверной сборке. Для двух наборов файлов ведутся отдельные манифесты: `deploy_server_manifest.json` и `deploy_client_manifest.json`. Режим `smart` отправляет новые и изменившиеся файлы, а `full` рассматривает все управляемые файлы; файлы с совпадающей контрольной суммой можно пропустить. Удаляются только устаревшие файлы, ранее учтённые соответствующим манифестом.

Файл `deployment/automodpack-server.conf.example` — пример конфигурации сервера AutoModpack. Скопируйте его вручную в `TARGET_DIR/automodpack/server.conf` и при необходимости отредактируйте сетевые параметры. Деплой защищает весь каталог `automodpack/`: он не устанавливает, не перезаписывает и не удаляет серверный конфиг или данные AutoModpack. Пустой `advertised-endpoint-host` и порт `-1` позволяют AutoModpack объявить адрес и фактический порт соединения Minecraft; отдельный IP или порт для режима `HOLEPUNCH` не задаётся. Не подставляйте `mods.innomc.ru` как адрес файлового хоста: это SRV-имя Minecraft-сервера.

После публикации клиентской сборки выполните на сервере `/automodpack generate` или перезапустите сервер, чтобы AutoModpack создал актуальный пакет. Если меняли `server.conf`, сначала выполните `/automodpack config reload`, затем генерацию; после изменения сетевых параметров дополнительно выполните `/automodpack host restart`.

Игрок должен хотя бы один раз подключиться к серверу: клиентский `client.conf` не содержит адрес сервера, а AutoModpack запоминает выбранный пакет и соединение после подключения. Затем включённая проверка при запуске обновляет выбранный пакет до загрузки игры. При недоступном сервере или сетевой ошибке обновление не гарантируется, и может запуститься уже имеющаяся локальная сборка. Для синхронизации собственной версии AutoModpack клиенту также нужен доступ к Modrinth; изменение некоторых загруженных модов или версии загрузчика может потребовать перезапуска игры.

В шаблоне отключена проверка download-secret (`validate-secrets: false`): скачать пакет сможет любой, кто знает адрес его endpoint. Файлы помечены как editable, чтобы локальные правки сохранялись, пока соответствующий файл в опубликованной сборке не изменился. Если изменится именно этот файл, клиент получит новую опубликованную версию. Editable-моды находятся в обычном каталоге `mods/`; изменённые или обновлённые JAR применяются после перезапуска игры.
